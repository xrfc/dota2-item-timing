# DOTA2 出装与装备时机分析：工程设计 v0.1
日期：2026-09-27
状态：设计稿；已核对上游代码，尚未用真实比赛响应验证数据可用性。
适用对象：个人学习项目。英雄、位置、版本由配置选择，不预设当前版本最优出装。

## 1. 产品目标与首版边界
输入比赛 ID 与 player_slot，生成个人出装时间线、同类对局的装备记录时机分布，以及可追溯的相似案例。
首版只支持一个英雄、一个位置、一个补丁版本、一个普通比赛模式；选择 3～5 件候选核心装备。
输出“与参考样本相比有什么差异”，不宣称某装备提高胜率或某次购买错误。
首版不实现实时辅助、最优出装、强化学习、全英雄覆盖、自建 OpenDota 服务、微服务和复杂前端。
输入不强制要求 account_id：匿名玩家也可以用 match_id + player_slot 标识。

## 2. 三个任务，分阶段交付
A. 事实重建：这场比赛记录了哪些购买事件，什么时候首次记录？
B. 条件比较：同英雄、同位置、同版本，类似早期经济与阵容下，装备首次记录时间如何分布？
C. 案例检索：在指定历史时刻，寻找此前状态相似的对局，展示其后购买路线。
A/B 是首版；C 在样本和状态字段可靠后增加。
后续模型预测的是玩家行为分布，不是装备因果价值。

## 3. 数据路线与第一道验收
首选 OpenDota API，原始响应原样缓存。STRATZ 或本地 replay parser 以后作为替换数据源。
最先准备 3～5 场自己的比赛，检查：
- 比赛版本、模式、阵容、玩家槽位是否可用。
- purchase_log 是否存在、完整，time 与 key 的含义是什么。
- 完整装备是否有独立记录，合成与配方如何处理。
- times、gold_t、xp_t、lh_t 的长度、单位和语义。
- 位置与段位字段的来源、时间和覆盖率。
- 与游戏内回放人工对照 10～20 次装备获取过程。
验收失败时，收缩为“购买日志浏览器”，或针对目标装备加入本地回放解析；不在不可靠标签上训练。

上游事实：
- OpenDota 类型定义含 purchase_log、gold_t、xp_t、lh_t 等解析字段，但实际响应可能缺失。
- compute.ts 对 purchase_log 过滤 recipe_ 和 ward_dispenser。
- purchase_time 是同类条目时间的求和；first_purchase_time 由日志计算。
因此不能直接把 purchase_time 当成完成时间，也不把过滤后的日志当作完整库存轨迹。
- lane_role 描述线路信息，不能简单等同于 1～5 号位。
- 当前账号段位不能默认为比赛当时段位。
- dotaconstants 可作为装备/英雄静态资料来源；必须绑定快照，不能默认当前资料适用于历史版本。

## 4. 时间与装备事件语义
统一使用从比赛开始计时的秒数，允许赛前负数；保留上游时间和来源。
每个装备事件记录 event_kind：
purchase_record / assembly_observed / inventory_observed / usable_observed。
首版默认 purchase_record，报告写“日志首次记录时间”。
只有人工验证或可靠库存观察支持，才升级为“合成完成时间”。
购买、合成、信使送达、主物品栏可用、首次使用是不同事件，不互相替代。
无法确认的时间为 null；缺失事件不是“没有购买”。

首版排除中立装备、赠送物品、消耗后永久增益和复杂升级链；重复购买保留事件，比较指标单独取首次合格事件。
物品名映射须保留原始 key；未知 key 记录质量警告，不能悄悄删除。
候选完整装备日志缺失时，不凭最终六格装备倒推出获得时间。

## 5. 数据表
matches：
match_id, patch_id, start_time, duration_seconds, mode, side_result, source, fetched_at, raw_hash。
players：
match_id, player_slot, account_id?, hero_id, hero_variant?, role?, role_source,
rank_bucket?, rank_observed_at?, rank_source?, quality_flags。
item_events：
match_id, player_slot, item_key, time_seconds, event_kind, provenance, verified, source_event_ref。
economy_samples：
match_id, player_slot, time_seconds, earned_gold?, net_worth?, xp?, last_hits?, source。
注意 earned_gold 与 net_worth 分列；没有经过字段语义核验就不填入。
decision_snapshots（后续）：
match_id, player_slot, cutoff_seconds, hero/variant, own_state, observed_context,
known_inventory?, field_availability。
analysis_results：
run_id, match_id, player_slot, finding_type, evidence, cohort_definition,
reference_count, outcome_observed_count, limitations, config_hash, dataset_hash。

每个事件和结果都能追溯到 raw JSON 与字段路径。
Pydantic 用于边界类型；批量样本用 Parquet；原始响应用 JSON；
SQLite 只记录抓取状态和分析索引。

## 6. 架构与模块
数据流：
数据源 → 原始缓存 → 标准化/质量检查 → 装备事件与状态 → 参考组/检索 → 分析 → HTML + JSON

单个 Python 包：
src/dota_items/
  sources/      API 访问、缓存、限流与重试
  domain.py     数据类型和单位
  normalize.py  上游字段映射、质量报告
  events.py     装备事件规则
  cohorts.py    参考组定义和样本计数
  retrieval.py  相似案例（第二版）
  analysis.py   分布比较与结构化结论
  report.py     HTML/图表
  cli.py        编排入口
configs/        英雄、位置、版本、装备、阈值
tests/          标签边界、时间截止、分组与端到端
research/       语义核验、评估、误判案例
data/           本地数据，默认不提交 Git
reports/        本地生成报告，默认不提交 Git

上游字段只在 sources/normalize 接触；下游不依赖 OpenDota 原始对象。
仅数据源与真正有替换需求的部分建立 Protocol；首版不建立十几个独立包和全套兼容层。

## 7. 参考组与分析方法
首版规则基线：
1. 同补丁、英雄/变体、模式、确认的位置。
2. 样本足够时，进一步按早期经济和段位分层。
3. 在同类样本中展示装备首次合格记录时间的中位数、四分位数和个人位置。
4. 同时展示装备观察比例、无记录比例和缺失率。
5. 参考样本不足时扩大可解释的经济区间，或只返回事实时间线；不跨版本静默混合。

角色可由用户手工确认；估计角色必须保存来源和置信信息。
如分析时刻早于角色推断所用数据，推断角色不能进入该时刻预测特征。

时机分布首版明确为“在观察到该装备记录的样本中”的条件分布。
它不是所有玩家的完成时间，也不是目标完成时间。
比赛结束而未观察到装备属于观察窗口结束，不能一律视为永不购买。
升级为全体样本时机建模后，需要生存分析或竞争事件处理。

显示阈值例如参考组至少 30 场，仅为可配置的工程起点，不是统计充分性的证明。
报告必须显示独立比赛数、有效事件数、时间跨度和缺失情况。
不要只收集胜局或职业局；职业局和普通局单独比较。
已解析比赛属于可获得的样本，不默认代表所有比赛。

## 8. 案例检索与模型扩展
第二版固定历史时刻，例如 10/15/20 分钟；只用该时刻及之前的信息。
先用标准化数值距离 + 类别过滤做最近邻，展示相似性、差异和样本后续行为。
库存不可可靠重建时，展示“此前记录事件”，不声称玩家当前持有这些装备。
敌方隐蔽物品状态不进入玩家视角特征。

机器学习任务候选：
- 未来 5 分钟是否首次记录候选装备。
- 下一件候选核心装备的类别，显式保留其他/无事件类别。
- 装备首次记录的时间到事件模型。

固定时刻样本需要足够的后续观察窗口；不足时标记截尾，不当成负类。
第一版实验可仅用观察窗口完整的样本，但须披露由此排除短局带来的偏差。
比较英雄/位置频率基线、规则分层、Logistic Regression、树模型。
不把胜率最大化作为首版训练目标，不把模仿常见购买行为叫作最优推荐。

## 9. 信息与数据泄漏
预测特征禁止使用最终 GPM、最终 KDA、最终装备、比赛胜负、未来经济和购买时间。
标准化、缺失填充、特征选择与阈值仅在训练/验证数据拟合。
相似案例只来自已结束的历史参考集，排除待分析比赛本身。
按 match_id 分组，同场比赛所有玩家和窗口在同一划分。
按时间保留更晚的测试比赛；有账号信息时增加按玩家外推检查。
版本切换重新评估，不直接复用当前装备价格、合成树或英雄标签。

## 10. 报告设计
首版页面四部分：
1. 我的装备事件时间线。
2. 某件装备的参考分布与我的位置。
3. 可核验的上下文：当时经济、等级/经验、补刀等已确认字段。
4. 数据质量、样本组成、局限与引用比赛。
后续增加“相似局势的后续路线”，让用户点开具体比赛。

示例文案（数字为示意）：
“该装备在你的日志中于 22:40 首次出现。参考组中观察到该装备的 86 场比赛，
首次记录时间中位数为 20:50，四分位区间为 18:30～23:10。你的记录落在该区间内。
这不能单独说明购买是否合理；当前资料没有确认送达时间。”
不输出伪精确的“决策正确率 84%”。

## 11. 评估与测试
数据质量：
- 人工复核事件类型和时间，分别报告准确性、时间误差和漏检。
- 缺失日志、配方过滤、赛前购买、重复购买、未知物品和未购买均有边界用例。
- 实际使用时间字段时核验暂停与时间基准。

统计/模型：
- 时机模型：中位绝对误差、分位区间覆盖率和宽度；截尾模型使用适合的指标。
- 分类模型：PR/AP、Log loss、Brier、校准，以及相对频率基线的提升。
- Top-k 案例/类别：Recall@k、覆盖率；它衡量行为检索或预测，不衡量战术最优性。
- 按比赛重采样报告不确定性；小样本结果明确标记。

产品：
- 用户能否确认时间线，理解参考组。
- 相似案例是否确实相似，差异是否被隐藏。
- 在证据不足时是否正确降级。
- 让少量朋友复核，记录具体错误，不只问“好不好用”。

## 12. 技术栈
Python + httpx + Pydantic + Pandas/Polars（二选一）+ Parquet +
SQLite + Plotly + Jinja2 + pytest + Ruff。
第二版才引入 scikit-learn 与一个树模型。
CLI 跑通后按需加 Streamlit 本地界面；多人服务阶段再用 FastAPI。
API key 放环境变量，不写日志或提交仓库。
抓取保守并发、缓存命中优先、超时和有限重试、429 按服务端提示退避；
实际配额和权限以使用时服务规则为准。

## 13. 学习与开发顺序（兼职粗略预算）
第 1 阶段，2～3 天：数据可行性探查、语义核验、选英雄/位置/版本/装备。
验收：3～5 场原始缓存，字段覆盖报告，人工核验记录；决定是否可继续。

第 2 阶段，约 1 周：单场标准化、装备时间线、静态 HTML。
验收：输入一场比赛和玩家槽位，一次命令生成报告；缺失数据明确降级。

第 3 阶段，1～2 周：收集初始几十至几百场符合范围的比赛（受实际可用性约束），参考组与分布比较。
验收：样本计数、质量、配置和数据指纹齐全；小样本不作强结论。

第 4 阶段，1～2 周：固定历史时刻的案例检索、人工复核。
验收：不使用未来特征，排除自身比赛，检索结果可以追溯。

第 5 阶段，按需：加入模型、公平基线和时间测试集。
验收：实验可复现；无提升时保留简单方法并解释原因。

## 14. 首批任务
1. 明确一个英雄、位置、模式和版本，以及 3～5 件装备。
2. 编写一页 scope 与时间语义说明。
3. 缓存 3～5 场实际比赛 JSON。
4. 生成字段覆盖率、缺失和事件质量报告。
5. 人工核验 10～20 次装备事件。
6. 实现 normalize 与事件表。
7. 实现单场 HTML 时间线。
8. 建立参考组、分布图与样本降级规则。
9. 增加比赛分组和历史时间截止测试。
10. 数据可靠后进入检索或模型阶段。
