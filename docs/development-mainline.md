# 主线开发流程：7.41f 阵容出装推荐

更新：2026-10-10。核对基线：[main c6a5e1f](https://github.com/xrfc/dota2-timing/commit/c6a5e1ff5eaa597d6c68567ef00f3acc973a64c9)。本文是**开发顺序与产品范围的唯一入口**；任务状态归 [roadmap](roadmap.md)，实际交付归 [project-status](project-status.md)，依赖约束归 [模块边界](module-boundaries.md)。新推荐接口和模块均为设计，尚未实现。

## 1. 目标与范围

输入双方十个英雄、推荐对象、位置，按 **7.41f** 给出常规核心、本局针对装备、条件备选、建议阶段，以及理由与局限。给十人推荐时复用单人用例；团队装备承担协调另行验收，不能把十份独立推荐称为联合优化。

- 用户已明确：7.41f 不采用命石输入。旧来源中的命石残留保留为历史原文，不进入新契约、标签或推荐规则。
- 显式校验 `patch=7.41f`，不用 latest 或未标版本的官网响应替代。
- 阵容支持能力潜力、条件与装备方向；不声称知道当前经济、库存、技能等级或下一件必买装备。
- 位置必须明确；缺失时补充或分别给有明确假设的位置方案，不凭英雄名固定位置。
- 保留魔瓶等阶段性装备；树枝、卷轴、消耗品不作为推荐目标。购买、合成、送达、可用状态分别建模。
- 当前不做路线/gank、精确购买时机、多用户服务或 GPU 训练。大规模 demo 不是规则版启动前提。
- 首个验收范围建议 3–5 个目标英雄、明确位置及有限装备集；具体名单尚待确定。对所有对局英雄检查覆盖状态，缺失不能当作没有威胁，不承诺一次交付全英雄推荐。

## 2. 复用已有能力

| 资产 | 使用方式 | 边界 |
|---|---|---|
| `knowledge/hero-capabilities/` | 候选事实及来源指针，逐项建立 7.41f 核验记录 | 当前快照 patch 未确认；734 条候选和15项来源核对不等于版本机制认证 |
| `storage.py`、Pydantic、检查入口 | 复用完整性、边界校验和交付方式 | 存储操作不进入推荐纯函数 |
| Gem、`sources/`、`data/` | 后续导入阵容、历史对照与实战状态 | 推荐不依赖解析器安装、回放下载或真实训练准入才能运行 |
| `workflow/` | 后续复用数据身份、实验记录，选择性适配报告 | item/route 预测契约不等于阵容推荐契约 |
| 学习与历史验收 | 理解、回归、发现问题 | L 勾选不等于工程完成；已审查八场不是未见测试集 |

现成方案预检：沿用 Gem、Pydantic、scikit-learn、JSON/JSONL；英雄身份可复用已冻结 OpenDota dotaconstants。它们不提供经本项目验收的 7.41f 推荐规则。首版用普通 Python 函数和版本化数据，不新增通用规则平台、微服务或付费服务。来源逐项确认版本，不能靠文件名认证内容。

## 3. 主线阶段与出口

任务状态仅维护在 [M01–M07](roadmap.md#当前主线741f-阵容推荐)，下表定义依赖与出口。

| 阶段 | 交付 | 出口 |
|---|---|---|
| M01 范围与契约 | 目标英雄/位置/装备范围；输入、输出、未知及错误契约 | 人数错误、重复英雄、目标缺失、错误版本、未知位置/英雄均有确定行为 |
| M02 7.41f 机制知识 | 技能/装备的机制、条件、来源、版本、核验记录 | 支持范围内必需事实有证据；冲突/未确认项不生效；命石残留不参与推导 |
| M03 阵容需求 | 敌方威胁、己方能力、目标职责 → 可追溯需求 | 需求能回到技能和条件；未知不等于不存在，不使用未来比赛字段 |
| M04 候选排序 | 英雄适配、应对价值、职责、阶段、代价 → 候选 | 先硬约束后软评分；功能重复、条件不满足、无候选可解释 |
| M05 最小交付 | 独立应用用例 + CLI JSON + 可读报告 | 离线可复现，记录知识/规则/版本身份；失败与部分覆盖明确；不破坏旧 CLI |
| M06 质量评估 | 人工复核案例、盲评、朴素基线与错误归因 | 提前确定指标/门槛，报告分母与覆盖；不达标缩小范围，不宣称提高胜率 |
| M07 回放与学习扩展 | 经验证的真实状态、可替换学习排序器 | 相关语义与新任务准入通过；购买模仿与建议质量分开评估 |

关键路径：M01 → M02 → M03 → M04 → M05 → M06。M02 先覆盖窄范围，不等全英雄机制完成才验证小闭环；其他英雄资料不足时只做部分分析。旧 D/V 可靠性任务继续维护，但坐标、XP、视野的全量核验不是赛前阵容版的统一前置条件。

## 4. 每个功能的开发循环

1. 选一个可独立验收切片，写用户输入、输出、失败行为、范围之外和任务编号。
2. 核对来源、已有能力和现成库；领域争议保留证据和未决项，不用代码把假设变事实。
3. 先明确契约、兼容和调用方向；跨模块选择在 [模块边界](module-boundaries.md) 记录理由、代价与替代方案。
4. 最小纵向切片：一个已核验机制 → 一个需求 → 一件候选 → 一条有来源的解释。不先创建大量空目录或抽象层。
5. 验证真实风险：机制正反例、版本冲突、信息不足、阵容顺序不变性、降级与序列化边界。
6. 相关检查通过后执行统一检查。文档变更检查链接、重建学习页面；不直接修改生成 HTML。
7. 审阅实现、契约、来源、状态与变更记录的一致性，不提交大型回放、私有数据和环境产物。
8. 开发分支提交与 PR，记录精确提交/检查结果。PR、合并、发布分别说明。

学习记录可复用 [任务模板](../learning/templates/task-record.md)，但完成 L01–L12 不是新主线的开发门槛。

## 5. 维护性与扩展性的完成定义

- **单一职责**：事实、战术规则、排序、渲染分开；CLI/HTML 不维护第二套规则。
- **显式版本**：patch/schema/knowledge/rules 分别标识；旧结果可追溯，规则变化生成新身份，不改冻结来源。
- **可替换**：学习排序只替换排序接口；训练框架不是知识读取或基础 CLI 的依赖。
- **可诊断**：输出命中规则、证据、过滤理由和缺口；区分输入非法、版本不支持、知识缺口、内部异常。
- **可回退**：保留上个知识/规则包及兼容说明；升级失败显式拒绝，不静默退到未知版本。
- **可测试**：纯逻辑用手算样本；适配器测 I/O 契约；端到端测用户路径；人工机制证据不能由自写分数测试替代。
- **可扩范围**：新增英雄/装备主要增加数据和规则；新增机制操作符才改领域代码，验证通过才声明支持。

交付必须包含限定范围、输入输出例子、实现位置、正反例、版本/兼容、证据/缺陷和复现命令。无模型不报模型指标，无客户端核验不写语义通过。
