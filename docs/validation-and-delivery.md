# 验证、实验与长期交付规范

设计日期：2026-09-29。状态：**待实施规范**，不是对现有 CI 或质量的承诺。
当前检查记录见 [工程审查](project-review.md)，操作与标注表见 [workflow](workflow.md)。

## 1. 三种“正确”分别验收

| 层次 | 问题 | 证据 |
|---|---|---|
| 工程正确性 | 同样输入能否稳定处理？失败是否破坏数据？ | 单元/契约/集成/故障测试、hash 与引用校验 |
| 游戏语义正确性 | 输出代表什么，时间与事件是否符合回放？ | 独立标注、双向匹配、未解决差异 |
| 分析有效性 | 样本和评估能否支持结论？ | 范围与分母、缺失分析、时间划分、基线与不确定性 |

三层不能替代：测试通过不是回放语义准确，单场语义准确也不是参考组有代表性。
每个发布物必须说明已通过哪层、覆盖哪些补丁/英雄/装备，未覆盖范围保留 unknown。

## 2. 测试分层与固定样本

| 层级 | 重点 | 运行场景 | 产物 |
|---|---|---|---|
| 单元 | 时钟、缺失、槽位、重复、过滤、首次事件 | 每次相关改动 | 快速结果；合成输入 |
| 适配器契约 | 真实形状 raw → 标准输出；每条引用与变换规则 | 每次适配器/契约改动 | 精简允许公开 fixture 与预期输出 |
| 存储集成 | 不同封装去重、过期缓存、迁移、目录搬迁、跨平台路径 | 每次存储/CLI 改动 | 临时数据集，前后计数和完整性报告 |
| 故障注入 | 解析中断、写文件失败、提交失败、锁竞争、取消 | 恢复协议改动与发布前 | 旧结果仍可用的记录和恢复结果 |
| 真实解析兼容 | 固定小回放集，含完整/截断/暂停/特殊购买场景 | 解析器升级、补丁支持声明前 | 版本能力矩阵、字段与语义差异 |
| 研究验收 | 去重、分母、截止、分组划分、无未来信息 | 数据集/统计/模型改动 | 可重算的指标与反例 |
| 产品验收 | 报告能核验、质量未知能解释、证据能定位 | 报告或本地界面改动 | 人工核对清单 |

默认 CI 不依赖在线比赛下载。大 Demo 可通过自有文件或校验过的受控测试资源运行，
记录来源与获取方法；未获允许的玩家数据不作为公开 fixture。
先修正现有 fake Gem 的 raw 结构，确保错误引用必然失败，再引入真实 fixture。

兼容矩阵每行包括 parser/adapter/schema 版本、补丁或 build（可未知）、平台、回放 hash、
实际验证的能力、通过/失败/未测与日期。只声明已测范围，不推断相邻补丁一定兼容。
升级原始 JSON hash 变化时，既检查字节变化也检查语义差异；字段排序变化不能冒充事件变化。

## 3. 人工语义验收

先确认比赛范围和目标事件，再建立标注规范与匹配容差，最后查看解析结果。
人工表记录 purchase / assembly / delivery / usable 等观察类型，时间线仍只纳入已定义的 purchase_record。
如果游戏画面不能直接证明与日志事件同义，标注“无法判定”，不要强行对齐。

3～5 场、10～20 条是初查规模；独立标注指定窗口或全场目标装备才构成漏检分母。
匹配须一对一；模糊、漏检与额外记录分别处置。报告每类事件的可判定数、匹配数、
漏检数、额外数、时间误差中位数/最大值、尚未覆盖的场景。

进入比较前：系统性时间偏移必须消除；目标装备语义歧义必须解决或排除；
所有已发现差异必须有修复、排除或保留未知的决定。没有足够标注时不发布整体“准确率”。
新补丁、新英雄或特殊装备规则超出现有覆盖，应补相应核验；无需每次界面改动都重标整套回放。

## 4. 参考组与抽样设计

先书面定义研究问题、纳入规则、目标装备、统计单位、观察窗口与排除规则，再收样本。
保留发现到排除的过程：候选来源数 → 独立比赛 → 有效玩家 → 日志可用 → 目标装备有/无记录。
查询缺失/未解析/无法下载单列，不把“拿得到的数据”当成全体玩家随机样本。

第一版每场选择指定英雄/位置的一名合格玩家，同一比赛只选一个事实集。
未来如果同场多个玩家满足范围，报告玩家样本数和独立比赛数，重采样与划分仍以比赛分组。
职业局、普通局、胜局与败局的组成写入报告；不得只保留方便支持结论的样本。

某装备的条件时间分布只在已观察到合格事件者中计算；无记录、日志不可用、观察不足分别统计。
不把无记录时间填成零、比赛长度或无穷，然后混入分位数。
小样本门槛只控制是否展示，不代表精度保证；不确定性需要结合样本量和采样结构解释。

先控制英雄/位置/补丁/模式。经济、段位、阵容细分会减少样本，不一开始同时细分所有条件。
预先记录放宽条件的顺序；不允许静默跨补丁或把未知角色当成确认角色。
数据不足时保留事实报告，这是正常产品结果。

## 5. 历史检索与预测实验协议

每个实验先完成一页任务说明，包含目标人群、时刻 t0、窗口长度、可见信息、标签、排除规则和基线。

| 任务 | 标签必须说明 | 基线 | 指标与边界 |
|---|---|---|---|
| 未来窗口首次记录 | t0 前未出现；未来窗口完整/受限；目标事件定义 | 训练集频率、条件规则 | PR/AP、Brier/Log loss、校准；不能解释为战术价值 |
| 下一装备类别 | 任意购买还是候选核心；重复/并列事件规则；其他/无事件 | 条件频率、简单分类器 | 类别覆盖、混淆矩阵、Top-k；无事件与观察不足分开 |
| 相似案例 | 特征截止、相似标准、案例池时间、排除自身 | 标准化距离 + 类别过滤 | 人工相似性/差异复核；用后续行为评估时遵守同样隔离 |
| 时间到事件 | 风险集、终止原因、比赛结束与日志丢失的区别 | 明确假设的简单时间基线 | 需另选适合竞争事件/删失的指标，不能仅报完成者 MAE |

划分顺序：先按比赛时间和 match_id 确定训练/验证/测试清单，再拟合特征变换。
同场不同玩家/时间窗必须在同一部分；新玩家外推检查仅在账号信息可用且适合保留时增加。
日期未知的比赛不能凭导入顺序进入“未来测试”。

标准化、缺失填补、特征选择和学习型距离只在训练集拟合；交叉验证时在每折训练部分重新拟合。
超参数、距离方案与阈值用验证集选择；最终测试集不用于调参。最终若用 train+validation 重训，
先冻结方案与数据范围，并仅对 untouched test 做一次最终评估。参见
[scikit-learn 关于预处理和数据泄漏的官方说明](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage)。

训练样本的历史快照只用 available_at ≤ t0 的信息。禁止最终 GPM/KDA/装备/胜负、未来经济，
以及利用整局信息得出的角色标签进入早期预测。玩家视角不使用未知敌方库存或未来可见状态。
案例池排除查询比赛；离线回测使用时间上早于查询且已经结束、符合可得性约定的历史案例。

每个实验保存 dataset/split/config/feature/label/代码/环境版本、随机种子、逐样本预测、
整体及关键子组指标、校准图和误差案例。按比赛重采样报告不确定性，不把同场多个窗口当成独立样本。
比较方法必须共享数据范围、标签和划分；复杂模型无稳定增益时保留简单方法。

## 6. 非功能目标与基准

| 目标 | 验收定义 | 何时要求 |
|---|---|---|
| 完整性 | 已选中的每个 artifact hash 和引用可核验；损坏可发现且不会作为健康缓存 | M1 |
| 可恢复 | 规定失败注入点不损坏旧提交；恢复到新数据目录后关键数量和结果一致 | M1 / 正式研究前 |
| 可迁移 | Windows/Linux 相对路径可解析；旧契约遇不兼容版本给明确提示 | 数据结构更新 |
| 可复现 | 固定数据/配置/环境后逻辑结果一致；浮点和随机实验声明容差/随机种子 | M2～M5 |
| 资源可控 | 超时、内存/文件大小/磁盘预算可配置，单场异常不会无限占用批次 | 扩大批处理前 |
| 性能 | 记录 1/10/100 场代表性基准；性能预算依据实测批准 | 引入并行或列式数据前 |

纯文档变更校验链接、术语、任务依赖和命令语法即可；不触发长时间全量重解析。
性能实验固定机器、数据集与缓存状态，分别报冷启动、缓存命中和规则重算，不能混成一个“每秒处理量”。
磁盘满、下载错误、权限失败、超时和取消都要有安全的用户说明，不只是堆栈。
没有测量基础时不设置看似精确的 99.9% 可用性或跨硬件耗时承诺。

## 7. 开发与发布节奏

每个任务遵循：关联 TODO → 定义契约/失败情形 → 最小行为测试 → 实现 → 相应层级验收 →
文档与兼容说明 → 小提交/评审 → 发布记录。每次同时进行的主要任务不超过两个。

单人阶段可在短功能分支自审，合作时用 PR；不要把数据、私钥或完整个人回放加入版本库。
软件语义版本与 schema 版本分开，文档变更不升级软件版本；0.x 阶段也必须解释破坏性变化。
正式发布记录包含新增能力、兼容范围、schema/迁移步骤、质量变化、已知限制和回滚方法。

建议维护矩阵：离线基础测试覆盖支持的 Python 版本；Windows 保留路径/编码/迁移检查；
解析器升级或数据契约变更才运行较重真实解析集；网络联调单独运行，不阻断纯离线日常开发。
依赖升级独立于功能改动，先固定当前可复现环境，再逐批升级并检查能力差异。

任务完成定义：验收正例与反例通过、输出可追溯、失败路径可解释、版本/迁移说明齐全、
roadmap 链接到提交或验收记录。仅有新模块、模型分数或截图不足以关闭任务。

## 8. 长期维护、可观测性与备份

日志与运行摘要至少含 attempt ID、阶段、耗时、输入/输出体积、事件保留/丢弃数、结果和原因码；
记录依赖版本，不打印密钥、聊天或完整账号资料。先本地结构化日志，不为单用户工具搭监控集群。

每次新增支持补丁或升级解析器更新兼容矩阵；每个重要发布做恢复演练；
有持续使用后按月或每轮迭代查看失败原因、上游变更、磁盘增长和未解决质量问题。
这是维护计划，不是已经启用的后台监控或定时任务。

备份不仅是 Git：原始证据、人工标注、元数据快照、数据集与实验清单均需备份。
缓存可重建，不能重新获得的原件与标注优先保留。清理先列影响，依据引用关系删除，
公开报告与数据导出单独检查身份信息；化名不等同不可重新识别。

## 9. 每阶段应留下的作品

| 阶段 | 可展示成果 | 学习与复盘材料 |
|---|---|---|
| M1 | 重复导入、损坏发现、中断恢复演示 | 数据契约、失败注入结果与设计取舍 |
| M2 | 一份可追溯语义核验报告 | 标注规范、误差与无法判断案例 |
| M3 | 自己比赛的可信参考组报告 | 抽样过程、分母、局限和用户反馈 |
| M4 | 固定时刻案例列表 | 特征截止测试与相似/不相似案例 |
| M5 | 基线与模型对照实验 | 复现清单、校准和无增益原因 |

对学习项目而言，能解释为什么采用某个边界、发现并定位了什么错误、怎样验证修复，
与最终效果同样重要。长期开发以这些可独立交付的成果累积，不以技术数量或模型复杂度累积。
