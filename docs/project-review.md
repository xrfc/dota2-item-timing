## 总体判断

方向适合个人学习：已有从原始数据到可见报告的闭环，能够逐步学习协议数据、数据工程、统计和模型。
当前最值得投入的是数据可信性与标签核验。直接扩充样本或训练模型，会把重复、缺失和时刻歧义带入结论。

已有的好基础包括：本地离线解析、保留 Gem JSON、有限的文件检查、SQL 外键与事务、
批量失败隔离、事件原始路径、保留重复购买、缺失不等于未购买，以及可离线查看的 HTML。
这些设计应该继续保留。

## 旧文档已纠正的地方

- 旧文档把本地解析器列为未来选项、写“尚未真实验证”，与已完成的单场公开回放验证不符。
- 旧文档的数据表、四类事件、null 时间、Parquet 与模块树属于未来蓝图，不能当作现有契约。
- 当前 SQLite 保存比赛、玩家和购买事件；不是“只存抓取状态”，也还不是研究数据仓库。
- 参考组、经济比较、检索和模型均未实现。首版实际交付是事实时间线。
- 原 TODO 缺少去重、缓存校验、故障恢复与验收证据，现已增加任务依赖和阶段门槛。

## 研究方法上应改进的地方

1. **标注要双向。** 从日志抽样只能检查已导出事件；需独立从回放标注目标事件，才有漏检分母。
   10～20 条只是发现明显语义错误的起点，不能证明总体准确率。
2. **先确认标签再控制条件。** 先确定“首次购买日志记录”对目标装备是否稳定有意义，再比较时间。
   日志不能表达某件装备的形成过程时，应缩小装备范围。
3. **明确分母和观察窗口。** 缺失日志不进“无记录”分母；短局和长局的末局观察比例不可不加说明地比较。
4. **把描述与预测分开。** 整局信息可以用于赛后描述，但不能进入历史截止时刻的预测特征。
   全知回放信息和玩家当时可知信息也要分开。
5. **先做简单而可靠的成果。** 一个英雄的可核验报告，比全英雄但没有可靠标签的模型更能体现工程与研究能力。
